Make the long run actually survive a kill, an outage and a truncated shard

Emma asked whether the run is fully resumable before starting it. Checking
found two ways it was not, both only reachable on a long unattended run:

- A dropped connection marked a batch 'error', which took those QIDs off the
  queue, and nothing ever put them back. A run resumed after an outage would
  have reported itself complete with holes in it. requeue_errors() now runs at
  the start of every run, bounded by an attempt count so a QID that fails for
  its own reasons is not retried forever.
- With the internet gone, every batch fails, and the walk would have sprinted
  through all 10,000 batches marking them errored in the time the outage
  lasted. A circuit breaker stops after five consecutive failures, leaving the
  queue intact, and says so on stderr with a non-zero exit.

Also: a batch is one gzip member, so losing power mid-write ends the member
mid-stream. That shard then raises on read, and -- worse -- anything appended
after the break is unreachable because decompression never gets past it. A
shard that will not read is now rewritten from the members that do, before
anything is appended. The interrupted batch is lost whole and re-fetched, which
is correct: the index is committed after the shard, so those items were never
recorded as held.

Emma also asked for certainty that whole items are stored, not a reduction.
Verified against the 1,000 already on disk: every one carries labels,
descriptions, aliases, claims, sitelinks and revision metadata, with 770
distinct properties across the batch and Q1001 at 461 KB with 342 properties
and 283 sitelinks. tests/test_wikidata_store_real.py now asserts that against
the real store -- full entity shape, qualifiers and references surviving, and
more than 100 distinct properties -- so a change that narrows what is stored
fails the suite instead of costing a four-hour run.
