wikidata-download: the two-queue walk, built and tested offline

Emma's design, mid-session: a fetch queue seeded with all 514,822 P2600 QIDs,
and an iteration queue of held items read for the relatives they name
(P22/P25/P26/P40/P3373). Anything named and not already known joins the fetch
queue; anything fetched joins the end of the iteration queue. The people it
reaches that carry no Geni ID are the objective, not a side effect.

The iteration queue is the shard sequence plus a cursor rather than a second
list -- items append in fetch order, so the end of the store is the end of the
queue, and scanning is a forward read of files already on disk.

Storage is many ordinary committed files: gzipped JSONL shards of 1000 items
under wikidata/items/, one gzip member per batch so compression works. No LFS,
no single large file. The resume index is SQLite under out/, derived from the
shards and rebuildable, never committed.

Live API for the whole seed set; the JSON dump is the fallback. 50 QIDs per
wbgetentities request is ~10,300 requests rather than 500,000.

Nothing has been queried. The pilot is BLOCKED-ON-USER-ACTION in queue.md item
4. CLAUDE.md now carries the standing rule that no ad-hoc Wikidata query is
permitted at all -- a stray check is how the run collects a 429 -- and todo.md
8b holds the questions that wait for the store, including Emma's recorded
prediction about the century distribution.

Two defects of mine, found by running it rather than reading it, fatal only at
scale: the fetch queue did a SELECT MAX(seq) per row and took over five minutes
to seed 514,822 (now 1.6s), and the scan rebuilt a half-million-QID set every
round. The ten-item tests were happy with both.

32 new tests, none touching the network. out/merged.ged (409 MB, generated)
noted as ignored by necessity -- the existing out/ line covers it and no .ged
pattern was added.
