Acknowledged technical inefficiency concerns regarding API query patterns

This is a pretty common complaint about agentic LLM behavior in general (not something unique to how Claude "feels" about wikis), and a few structural reasons tend to explain it:

No persistent sense of state across calls. Each tool call is decided fresh based on the current context, not against a running budget or plan. Without an explicit "I've already fetched section X, don't fetch it again" instruction, nothing stops the model from re-querying the same page, querying page-by-page instead of batching, or hitting an API once per fact instead of once per task.

Optimizing for "get the answer" over "be a good API citizen." The model's implicit objective during a task is usually "resolve the user's request," not "minimize requests to this specific service." Efficiency, backoff, and courtesy toward rate limits aren't things it reasons about unless prompted to, or unless the tool/agent harness enforces them.

Missing infrastructure, not missing judgement. A lot of what looks like "aggressive" querying is actually a harness problem: no caching layer, no dedup of identical requests, no batching of what could be a single query call with titles=A|B|C instead of three separate calls, no exponential backoff on 429s, no queue/throttle. If the surrounding code (or the agent's own tool-use loop) doesn't implement these, the model will just keep firing requests as fast as it decides it needs data, and retry immediately after a 429 rather than backing off.

Wiki APIs specifically are easy to misuse. MediaWiki's API supports batching (multiple titles per call, generator= params, continuation tokens) but it's easy for an agent to instead do the naive thing: one search, then one fetch per result, then one fetch per section — because that mirrors how a human would click through a wiki rather than how you'd script against its API.

If you're seeing this in something you're building (an agent, a scraper, whatever), the fix is usually external to the model: add a caching/dedup layer, batch requests, respect Retry-After headers, and give the agent an explicit instruction/tool design that nudges it toward batched queries instead of many small ones. Want help designing that layer, or is this happening inside a specific tool you're using?

Reading through that transcript, the plan Claude Code wrote down is basically sound on the parts you were most worked up about — SPARQL for cheap bulk structure, JSON entity endpoint for the expensive per-item pulls, backoff-from-the-start instead of backoff-after-getting-yelled-at, resumability. That's the right shape.

A few things I'd flag before your PC session runs with it, though:

"Commit and push per item" is going to hurt you. For 500k items, a git commit+push per entity means 500k commits (or 500k tiny diffs in one growing working tree) — git gets brutally slow well before you're done, and GitHub will start rejecting oversized pushes or you'll blow past reasonable repo size long before item 100,000. What you actually want is: write JSON to disk continuously (one file or an append-only store per item), and commit+push in batches — every N items or every few minutes, whichever comes first. The "never query twice" property doesn't require a commit per item, it requires a durable on-disk record — the commit cadence is a separate knob.

For resuming/dedup, don't rely on git history — track state explicitly. A local SQLite table (or even a flat file) of QID → done is instant to check; grepping git log or ls-ing a directory of 500k files repeatedly is not. This is also where you'd track retry counts / last-error per item if something fails.

At 500k items, reconsider hitting the live API at all for the initial seed set. Wikimedia explicitly steers bulk consumers toward the Wikidata JSON dump rather than the live entity API — it's a weekly full/truthy dump you stream and filter locally with zero rate-limit risk. If your 500k Geni-linked seed set can be identified via a property filter (P2600) that's cheap in SPARQL, you could: (1) SPARQL for the QID list, (2) pull matching entities out of the dump instead of hitting Special:EntityData 500k times live. The expansion phase (walking P22/P25/P26/P40 to find items without a Geni ID) is where you genuinely need live incremental queries since you don't know the frontier in advance — that's the part actually suited to the careful-backoff live approach. Worth having Claude Code think through whether the seed and expansion phases should use different strategies rather than one uniform "hit the API slowly" plan for both.

One more Wikimedia-specific gotcha: the SPARQL endpoint (query.wikidata.org) has its own separate limits from the action/REST API — a 60-second query timeout and its own throttling — so "SPARQL is cheap" is true per-query but you'll still want batching/pagination logic there too, not just on the entity-fetch side.

8a-revised — Wikidata build: dump-first + batched writes

Storage/commit cadence (correction to prior draft):

  • Write each item's full JSON to disk immediately as it's fetched — one file per QID (or an append-only JSONL shard), never re-fetched once present.
  • Commit and push in batches, not per-item: every 500–1000 items or every N minutes, whichever comes first. A killed run resumes by scanning what's on disk (or a state table, below), not by walking git history.
  • Maintain a lightweight local state store (SQLite or a flat manifest file) mapping QID → status (done / pending / errored) so resumability and dedup don't depend on git or filesystem scans of 500k files.

Two-phase sourcing, not one uniform live-API loop:

  1. Seed phase (~500k Geni-linked items):
    • Use the Wikidata JSON dump (weekly full or truthy dump) as the primary source, not live per-entity fetches.
    • Get the target QID list via one (or a handful of paginated) SPARQL query for P2600, then stream-filter the dump against that list locally. Zero rate-limit exposure for the bulk of the volume.
    • Live entity API (Special:EntityData/Q….json or wbgetentities) is the fallback only for items missing from the dump snapshot (created/edited since the dump was cut).
  2. Expansion phase (walking P22/P25/P26/P40 to items without a Geni ID):
    • This part is inherently incremental/frontier-driven, so it stays on the live API.
    • Same backoff discipline as before: descriptive User-Agent with contact info, exponential backoff, honor Retry-After, find sustainable rate by experiment, back off the instant throttling appears.
    • SPARQL also has its own separate limits (60s query timeout, its own throttling) independent of the entity API's — batch/paginate SPARQL calls too, don't treat it as free just because it's cheap per-query.

Net effect: the expensive, throttle-prone live path only has to carry the expansion frontier, not the full 500k seed set — which should cut total live-API volume by a large margin and make the backoff tuning much less punishing to get right.
