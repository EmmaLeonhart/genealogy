# Audit — `Q141223488` *Fersen*, created twice as a patronymic

**Emma, 2026-08-30**, adding to the patronymic complaint: *"https://www.wikidata.org/wiki/Q141223488
and the one merged into it were both just completely erroneous too"*.

## What the two items are

| item | state |
| --- | --- |
| `Q141223488` | label `Fersen` (`en` and `mul`), one statement: `P31` *instance of* → `Q110874` **patronymic**. Created 2026-08-30 18:04 by `#quickstatements`. |
| `Q141223718` | **redirects into `Q141223488`** — the one she says was merged in. |

So we created the same name item twice in one run and something merged them.

**`Fersen` is not a patronymic.** It is the Baltic-German noble family name — *Hans Axel von
Fersen*. A patronymic names the father; `Fersen` names a house.

## Why the classifier said patronymic

`scripts/namemodel.PATRONYMIC` is

    re.compile(r".+(sen|son|sson|datter|sdatter|dotter)$", re.I)

and **`Fersen` ends in `sen`**. Morphology alone cannot separate `Fersen` from `Hansen`.

The module already knows this and already has the answer. `patronymic_or_surname()` implements
**Emma's own test, 2026-08-26** — *"If father has -son or -sen then it's a surname"* — refined so
it does not swallow genuine patronymics:

| test | verdict |
| --- | --- |
| the token is one of the **father's own** tokens | **family** |
| the stem matches the father's **given** name | patronymic |
| neither | undecided, kept as patronymic |

Checked directly:

    patronymic_or_surname("Fersen", "")                      -> patronymic
    patronymic_or_surname("Fersen", "Hans Axel von Fersen")  -> family
    patronymic_or_surname("Olsen",  "Ole Hansen")            -> patronymic

The rule works. **It was never given the father.**

## The actual defect: the generator dropped the father on the floor

`scripts/build-garborg-name-items.py` built a `fields` dict of `("givn", "surn", "nick",
"marnm")` — no `father_name` — and called `classify_fields(**person)`. With `father_name=""`,
`patronymic_or_surname` returns `"patronymic"` on its first line. **Every `-sen`/`-son`/`-datter`
token in every batch became a patronymic name item.**

It also built `father_of` from `derived-family.csv` and used it only to look up the father's
*QID*, never his *name*, and it never passed `father_name=` to `statements_for` either — though
that function's own comment says *"`father_name` is what turns a `-sen` token into the right kind
of statement."*

**Fixed 2026-08-31.** The family pass now runs before the label pass so the fathers' labels load
in the same sweep; `father_name` goes into each person dict and into `statements_for`. The fathers
are **not** added to `ids`, so this does not widen who gets an item.

## What it changed in the very next batch

`Jenssen` was queued for creation as a **patronymic**, to be attached with `P5056` to four people
— Olufine Bergithe, Hilma Petrine, Iver Emil and Louise Helmine — whose father is
**`Hans Otto Kristian Jenssen`**. The father carries the token, so by her rule it is a family
name, and all four statements were wrong. They are gone; the batch proposes `Erikson` instead,
where the bearers' father genuinely is an `Erik`.

The carry-forward fell 269 → 258, because tokens that stopped being patronymics merged into
family-name entries that already existed.

## Not fixed

`Q141223488` itself still says `P31` → `Q110874`. Correcting or merging it is a Wikidata edit and
is listed in `reports/merges-to-do.md`, not done here.

One duplicate line survives in the generated batch — `Q141216607` gets the same `P5056` statement
twice, because `Hans Erikson` carries `Erikson` in **both** `GIVN` and `SURN` and
`classify_fields` returns the pair twice. It is left alone on purpose: `CLAUDE.md`
§ *Duplication is a DOUBLE-EDGED SWORD* forbids adding a de-duplication pass, and QuickStatements
no-ops the repeat.
